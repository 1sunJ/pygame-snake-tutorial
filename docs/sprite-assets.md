# Sprite Asset Specification

How the game's pixel art is built, and the dead ends that shaped it.
For how the assets are wired into the game, see [apply-sprites.md](apply-sprites.md).

---

## 1. The resolution decision

| Topic | Decision |
|---|---|
| Sprite size | 16x16 |
| Internal view | 320x320 board (20x20 cells), 338 tall including the footer |
| Window | 640x676 — the view scaled x2 with nearest-neighbour |
| Palette | Leaf green on a warm charcoal board |
| Production | Generated by `tools/make_sprites.py`, no new dependency |

**The scale factor is the whole point.** An earlier version drew 32x32 sprites
straight into a 640 window, so one art pixel was one screen pixel. Every
technical box was ticked — hard edges, no anti-aliasing, four-colour ramp — and
it still did not look like pixel art, because at 1:1 the pixels are too small to
see. Pixel art reads as pixel art when the blocks are visible.

Halving the art to 16x16 and scaling the whole frame x2 makes each art pixel a
2x2 block on screen. Same window size, same grid, completely different look.

Two rules follow:

- **The scale factor must be an integer.** A x1.5 scale would land art pixels on
  half-screen-pixels and blur them.
- **Everything must be drawn at the internal resolution**, including text.
  Anything drawn at window resolution keeps fine detail the rest of the frame
  does not have, and immediately looks out of place.

## 2. Common requirements

| Property | Value |
|---|---|
| Dimensions | 16x16, square, no exceptions |
| Format | PNG-32 with alpha |
| Background | Transparent |
| Anti-aliasing | Off. No blended pixels on any edge |
| Body thickness | 14px, centred, 1px margin each side |

The 14px body thickness is the critical number. Head, body, corner and tail must
all use it, or the snake changes width as it moves.

## 3. Asset list

Five files. The board background is **not** a file — see section 5.

| File | Purpose |
|---|---|
| `snake_head.png` | Head, facing right |
| `snake_body.png` | Straight body, horizontal |
| `snake_corner.png` | 90-degree turn, connecting left and down |
| `snake_tail.png` | Tail tip, body to the right |
| `food_apple.png` | Food |

```
assets/
  sprites/
    snake_head.png
    snake_body.png
    snake_corner.png
    snake_tail.png
    food_apple.png
```

"Sprite" here means an image file in the general sense. It does **not** refer to
`pygame.sprite.Sprite`; `snake_game.py` tracks the snake as coordinate tuples
and does its own collision checks, so that class is unused.

## 4. Per-asset notes

### Edges that must bleed

This is the rule that makes segments join into one continuous tube. A sprite
must fill the cell edge on every side where another segment attaches, and keep
its 1px margin everywhere else.

| Sprite | Bleeds on |
|---|---|
| `snake_body` | left, right |
| `snake_corner` | left, bottom |
| `snake_head` | left only |
| `snake_tail` | right only |
| `food_apple` | nothing — margin on all four sides |

Food is the only sprite with no bleeding edge, because it is a discrete object
sitting inside a cell rather than part of a chain.

### Shading

Symmetric across the tube: brightest along the centre line, darker toward both
edges, outline on the silhouette. At 14px that is 4 rows of highlight, 2+2 of
base, 2+2 of shadow, 1+1 of outline.

It has to be symmetric because the sprites are rotated. A tube lit from the top
looks right on its own, but the highlight rotates with the sprite — horizontal
body lit on top, vertical body lit on the left, corner lit on its outer arc — so
every joint shows the bright band jumping sides. Symmetric shading is identical
under 90-degree rotation, so joints line up.

### Head

Same thickness as the body, distinguished only by the rounded snout, two 2x2
dark eyes and a 2px tongue. Widening the head was tried at 32px and abandoned:
there was room for exactly 1px of extra width, and 1px renders as a step at the
neck rather than a curve. At 16px there is no room at all.

The eyes went through three versions. White eyeball with a dark pupil read as
two white squares. A dark eye with a 2px highlight read as a bullseye. At 16px
there is no room for a highlight, so they are plain 2x2 dark blocks — which
become a clear 4x4 on screen after scaling.

### Tail

Thickness falls off as `t**0.55` rather than linearly. A linear taper produced
straight edges that read as an arrowhead.

## 5. Board background — no file

The background went through four versions:

| Version | Result |
|---|---|
| Checkerboard tile + per-pixel noise | Noise read as smudging; the 1px line ran along only two sides of each cell, so the grid looked off-register |
| Rounded plates with a darker gap | Clean, but 400 repeating plates competed with one snake and one apple for attention |
| Flat fill + corner dots + smooth vignette | Background finally receded, but a smooth gradient is the one thing pixel art never has |
| Flat fill + corner dots + **dithered** vignette | Current |

**The tile was the problem, not its colours.** Any pattern repeated 400 times
asserts itself. All the player needs from the background is to judge whether the
head and the food share a line, and one dot per cell corner does that.

The darkening toward the edges is now two flat colours mixed with a 4x4 Bayer
dither instead of a gradient, so the transition is made of visible dots rather
than a continuous ramp. Built in `Renderer._build_board`; there is no asset,
so the background adapts to any grid size, while the sprites stay tied to
`CELL_SIZE` being 16.

## 6. Rotation

Five sprites produce 15 on-screen variants.

| Source | Default | Derived | Total |
|---|---|---|---|
| `snake_head` | faces right | up, down, left | 4 |
| `snake_body` | horizontal | vertical | 2 |
| `snake_corner` | left + down | 3 other turns | 4 |
| `snake_tail` | body to the right | up, down, left | 4 |
| `food_apple` | — | — | 1 |

`pygame.transform.rotate` takes counter-clockwise degrees: right 0, up 90,
left 180, down 270. Corners are keyed by which two sides they connect. Rotation
by multiples of 90 moves pixels exactly, so nothing is resampled.

## 7. Palette

| Role | Hex |
|---|---|
| Snake outline | `#1D5226` |
| Snake edge | `#2E8C3C` |
| Snake body | `#4FC259` |
| Snake highlight | `#8ADE7C` |
| Apple body | `#FF4757` |
| Apple highlight | `#FF8A94` |
| Apple leaf | `#A5E063` |
| Board | `#26201A` |
| Board dimmed | `#201B16` |
| Cell corner dot | `#3C342A` |
| Frame | `#181410` |

An earlier palette put a mint snake on dark navy and did not work. Navy carries
enough chroma that the board asserted its own colour instead of receding, and
being cool like the snake it fought the green rather than separating from it.
The red apple sat awkwardly on it too. A warm, low-chroma board fixes both:
green reads naturally against warm neutrals, and the apple settles into the
scene. The snake green was pulled from cyan toward yellow at the same time.

Board colours live in `settings.py`, not in the generator, since the background
is drawn at runtime.

## 8. Regenerating

```bash
python3 tools/make_sprites.py
```

The generator is a build tool, not game code — the game needs only the PNGs.

A caveat worth recording: coordinate-generated art is clean and regular, but it
does not carry the character of hand-drawn work, and its curves have irregular
stair-steps where a human would smooth them into even runs. The output is best
treated as a starting point that can be refined by hand in Piskel or Aseprite,
as long as the sizes and bleeding edges above are preserved.
